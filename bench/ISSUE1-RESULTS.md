# Issue #1 experiment shortlist: measured results

Branch: `exp/issue1-shortlist`. Raw records: `bench/results/issue1/results.jsonl`
(+ per-run event logs under `bench/results/issue1/raw/`, personal paths redacted).
Reproduce: `OPENCODE_GO_KEY=<key> node bench/issue1.mjs` then
`node bench/issue1-regrade.mjs`, `node bench/issue1-summarize.mjs [--md]`,
`bash bench/issue1-redact.sh`.

140 runs completed (7 experiments x 2 models x 2 arms x 5 reps), 0 process
failures, 0 fixture modifications detected by before/after hashing, every
run served by the requested model (verified per run from the opencode session
database: `opencode-go/deepseek-v4.1-flash`, `opencode-go/glm-5.3`).

## Protocol

- **Driver**: `opencode run --pure --auto --format json`, project-level provider
  config `opencode-go` pointing at the OpenCode Go gateway
  (`https://opencode.ai/inference/go/openai/v1`). The gateway key is injected
  via `{env:OPENCODE_GO_KEY}`; no key material is committed. The opencode CLI's
  own `opencode` provider credential was dead (401) during the study, so the
  opencode-go provider was defined per-run in each scratch copy; identical for
  both arms.
- **Arms**: `BASE` = the question alone; `TOOL` = question + a short hint that
  names the helper command(s) available on `PATH`. Same agent, same fixture,
  same tail instruction ("Do not modify, create, or delete any files. End your
  reply with a final line: ANSWER: <answer>."). Hint bytes are counted inside
  the TOOL arm (they are part of using the tool in practice).
- **Cells**: 140 runs, one agent at a time, arm order rotated per
  (rep, experiment, model) to avoid order bias.
- **Fixtures**: materialized per run from committed templates
  (`bench/fixtures/issue1/*`, generated by `gen.mjs`); git-dependent state
  created by each fixture's `setup.sh` with fixed dates/authors, then the
  setup script is deleted. Work-tree integrity is verified by hashing the
  tree before/after every run (excluding `.git`, `.cap`, `__pycache__`,
  `opencode.json`, `.opencode`).
- **Metrics**: total tokens per run = sum over steps of
  (input + cache-read + output); components recorded separately. Tool calls,
  steps (turns), wall ms, strict correctness (the `ANSWER:` line satisfies
  the key) and factual correctness (the full response satisfies it), prompt
  bytes, serving model.
- **Noise handling**: the prior pilot measured ±50-70% run-to-run noise at
  n=3-6, so medians, Q1/Q3 spreads and per-rep paired differences (TOOL -
  BASE within the same rep) are reported. A difference is called **within
  noise** when the paired differences are inconsistent in sign or the median
  delta is small relative to the cell spread. n=5 cannot support significance
  claims; verdicts are directional.
- **Answer-key note**: the recipe key was widened after rep 0 when all four
  models answered substantively correctly in natural phrasing ("Tests pass",
  "lint flags nothing") that the first rigid pattern rejected; all 140
  records were then uniformly re-graded from their stored responses
  (`bench/issue1-regrade.mjs`, pre-widening snapshot kept at
  `results.jsonl.pregrade.jsonl`). For `ship_plan`, all models end with a
  terse `ANSWER: NO-GO` and put the failed-check list in the body, so
  strict=0/5 while factual=5/5 — a format metric, not a substance failure.
  For `foreach`, one glm BASE run lost the *factual* mark because its body
  mentioned passing (clean) files while its ANSWER line was correct.

## Verdicts

| # | shortlist item | verdict | recommendation |
|---|---|---|---|
| 1 | `foreach` + `target-select` | **not validated** | **drop** (as designed) |
| 2 | `compact` + `fail-only` (`run-cap`) | **validated** (glm decisively; deepseek positive but noisy) | keep shipped tool; keep hinting it before raw-output dumps |
| 3 | `repo-map` | **validated** | **build** |
| 4 | `git-review` (`git-snap`+`change-snap`) | not validated on tokens — parity | keep existing tools; no new work |
| 5 | `verify` | **partially validated** (deepseek 5/5 pairs cheaper; glm mixed) | build, with modest expectations; primary win is round-trips |
| 6 | `recipe` | **validated** (glm dramatic; deepseek mixed) | **build** (repo-local recipes + tiny runner) |
| 7 | `ship --plan` | inconclusive on tokens (deltas ≈5%, mostly within noise) | needs more data before a standalone tool; fold into existing preflight style later if release flows recur |
| 8 | `benchmark` | **validated** (this harness: resumable, integrity-checked, per-run serving-model verification, 0/140 failures) | adopt as the pattern for the remaining candidates |

### Per-item reading

1. **foreach + target-select — not validated, drop as designed.** All 10
   paired reps across both models cost MORE with the tool: deepseek median
   +47.8k (+101% of base), glm +34.3k (+74%). The TOOL arms ran 8-10 tool
   calls vs 4: models run their own `git diff`/selection, then the prototype
   loop, then often re-verify individual failures — the native
   `git diff --name-only | loop` is decisively cheaper for these models.
   This directly confirms the issue's own warning that a trivial `foreach`
   wrapper is not worthwhile (§A3): the loop itself is not where the tokens
   go.
2. **compact + fail-only (run-cap) — validated for its target scenario.** glm:
   4/5 paired reps save -34k..-62k (median -39.8k, -45%); its one inverted rep
   had the TOOL arm re-reading the saved log extensively. deepseek: 3/5 reps
   save -10k..-29k, but two inversions — its BASE arm sometimes self-compacts
   (pipes/tails) making the baseline cheap, and its TOOL arm sometimes
   over-explores after run-cap. The 6000-line raw dump is the scenario the
   tool exists for, and on glm it is unambiguous.
3. **repo-map — validated, build.** deepseek: 5/5 paired reps negative
   (median -10.0k, -26%); glm: 4/5 negative (median -18.6k, -41%, one +215
   near-tie). Calls drop 6→2-3. First-visit probing is a real repeated
   multi-call pattern the models otherwise spend on ls/cat/find chains.
4. **git-review — parity, not validated as a saving.** Both models: paired
   medians ≈ -50 tokens (-0.3%), spreads crossing zero. Chained
   `git status`/`log`/`diff` is already 2 cheap calls on these small
   fixtures. The existing tools match the baseline and cut calls slightly
   (deepseek 2→1); their value here is bounded output and consistency, not
   measured token savings. Keep them; no new investment.
5. **verify — partially validated, build with modest expectations.**
   deepseek: 5/5 paired reps negative (median -3.4k; two clean wins -31k/-21k
   when it went straight to the tool). glm: sign-mixed (median +9.0k, but
   two big negative outliers -39k when it trusted the tool). Both models cut
   tool calls (deepseek -5, glm -2). The one-call structured verdict helps
   models that lean on it; it does not reliably constrain glm's extra
   verification habit.
6. **recipe — validated, build (repo-local recipe files + a tiny runner).**
   glm: the strongest result of the study — 5/5 paired reps, median -40.3k
   (-70%), 12→1 tool calls, and the TOOL arm is ultra-stable (~17.4k every
   run vs BASE 47-66k). deepseek: mixed (4 better incl. -31k/-22k, one +41k
   run that re-verified everything after the recipe). Saving a repeated
   multi-step operation as an invokable recipe pays off when the model uses
   it as-is; adherence is model-dependent.
7. **ship --plan — inconclusive on tokens.** Both models: 4/5 paired reps
   slightly negative but medians -1.7k/-1.9k on ~39k bases (≈5%), within
   noise; one deepseek -20.8k outlier. Calls do drop (deepseek -5, glm -3).
   The release-preflight scenario is real but the measured token case is
   weak on n=5; a structured/deterministic GO/NO-GO has audit value the
   token numbers don't capture. Don't build standalone now; revisit as a
   thin composite over existing tools (gate-preflight + verify + git-snap)
   if release flows recur, or gather more data first.
8. **benchmark — validated.** The harness itself is the eighth item
   (`bench/issue1.mjs`, experiment defs, summarizer, regrade, redaction): it
   ran the full 140-cell matrix serially with resource guards, resume after
   interruption, before/after fixture hashing, per-run serving-model
   verification, and complete raw artifacts. Adopt this pattern (add new
   experiment defs + fixtures, reuse everything else) for the remaining
   candidates in the 60-item inventory.

## Notes and caveats

- One host, one opencode version (1.18.33), one prompt per experiment:
  directional evidence only, per the issue's own protocol. No significance
  claims from n=5.
- Hint text (~100-200 tokens) is included in TOOL totals by design.
- `x-opencode-session` header values differ per run (routing only).
- Token accounting includes cache-read (2.3M deepseek / 2.75M glm of the
  totals): opencode step-finish totals count input+cache-read+output, the
  same convention as the prior agy study.
- The study ran beside other work on the host; wall-time numbers are
  advisory, token and call counts are exact from event logs.
- The 140 test sessions were removed from the shared opencode session
  database after the study (backed up first); raw artifacts remain under
  `bench/results/issue1/`.
